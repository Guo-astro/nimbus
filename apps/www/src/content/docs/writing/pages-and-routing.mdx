A page is a `.md` or `.mdx` file under `src/content/docs/`. Its path on disk is its URL and its place in the [sidebar](/navigation/sidebar) — there is no separate routing or navigation config.

## File to URL

| File | URL |
|---|---|
| `src/content/docs/get-started.mdx` | `/get-started/` |
| `src/content/docs/guides/styling.mdx` | `/guides/styling/` |
| `src/content/docs/guides/index.mdx` | `/guides/` |

The URLs end in a slash with Astro's default `trailingSlash` and `build.format`; see [Links and trailing slashes](/configuration#links-and-trailing-slashes). Slugs are lowercased and folder `index` files collapse to the directory URL. A directory's `index.mdx` becomes the landing page for that section.

## Custom Astro routes

Files you add under `src/pages/` use Astro's native routing and rendering semantics. In a server-output project, a page or endpoint renders on request by default; set Astro's `prerender` export when you want to make the choice explicit:

```astro title="src/pages/status.astro"
---
export const prerender = false;
---

<h1>Service status</h1>
```

```ts title="src/pages/api/ping.ts"
export const prerender = false;

export function GET() {
  return new Response("pong");
}
```

Use `export const prerender = true` to emit a custom route as static output during the build. No Nimbus route registration or allowlist is required.

This boundary is not limited to `prerender`. Dynamic segments, endpoint methods, redirects and responses, and other native Astro route behavior remain controlled by the route itself. Nimbus only intervenes when a route claims the exact pattern of a configured canonical content route, package-injected infrastructure, an active feature, or a published content entry.

Nimbus's `rendering` configuration controls canonical content-collection routes, not other files under `src/pages/`. Files scaffolded for `llms.txt`, Markdown alternates, Open Graph images, and `robots.txt` belong to your project and may use Astro's native rendering behavior like any other route.

## Page modes

Every page renders inside `DocsLayout` by default — sidebar, table of contents, breadcrumbs, prev/next. Opt a page out of all chrome with `mode`:

```yaml
---
title: Welcome
mode: custom
---
```

`mode: custom` is for landing pages and bespoke layouts. Per-column toggles (`sidebar: false`, `tableOfContents: false`) turn off individual pieces without going fully custom — see [Layouts](/styling/layouts).

## Drafts

`draft: true` keeps a page out of production builds and the `llms.txt` indexes, while still rendering under `astro dev` (treated as `noindex`). Use it for work in progress.

```yaml
---
title: Experimental feature
draft: true
---
```

## Redirecting a sidebar entry

`external_link` rewrites where the sidebar links a page without changing where it builds — useful for pointing an entry at another section or an off-site URL. See [Redirects](/navigation/redirects).

## Other collections

`src/content/docs/` is the primary collection, mounted at the site root. Additional collections (a `blog`, an `api`, a versioned `docs-v2`) are served at their own URL: where their route file is, or `/<name>` by default (see [Collection URLs](#collection-urls)). Register them in `src/content.config.ts` with the factories from `@cloudflare/nimbus-docs/content`.

Nimbus's `docsCollection()`, `partialsCollection()`, and `componentsCollection()` factories prepare content for links, alternate Markdown/MDX versions, `llms-full.txt`, and partial headings automatically. If you register a loader that stores Markdown bodies directly, wrap it with `withNimbusMarkdown()`:

```ts title="src/content.config.ts"
import { defineCollection } from "astro:content";
import { glob } from "astro/loaders";
import { withNimbusMarkdown } from "@cloudflare/nimbus-docs/content";

export const collections = {
  blog: defineCollection({
    loader: withNimbusMarkdown(
      glob({ base: "./src/content/blog", pattern: "**/*.{md,mdx}" }),
    ),
  }),
};
```

The wrapper preserves the loader's methods and lifecycle. Use it when a loader stores entries with a Markdown `body`.

A page collection's files can live anywhere. A glob over a folder outside `src/` (a checkout of another repository, a shared folder in a monorepo) gets callouts, components, citations, links, collision checks and lint exactly as a page under `src/content` does. A loader with no files (a CMS) gets everything that reads the entry: routes, the sidebar, citations, links, Markdown versions, `llms.txt`, search and URL collision checks. Its pages are Markdown only, so no callouts or components, and `nimbus-docs lint` names the collection as not inspected. Such a loader must check its ids for duplicates before it writes, because without a file Nimbus can't tell a collision from an update. In a hand-written glob, two files with one slug fail the build, except a byte-identical copy, which Astro's glob never writes; the factories catch that too. For content in another repository or a CMS, see [Content from other sources](/writing/content-sources).

Page collections come from the helpers: a collection made with `docsCollection()`, `componentsCollection()`, or a `withNimbusMarkdown()`-wrapped loader becomes pages — routed, indexed, and included in search, the sitemap, `llms.txt`, and Markdown versions. Every other collection is plain Astro data: Nimbus doesn't route it, index it, check it, or fail on it, no wrapping is needed, and `getCollection()` works as in any Astro site. Collection names carry no meaning — there is no reserved `_` prefix. `apiCollection()` is the purpose-built exception for API references because Nimbus supplies its renderer.

## Collection URLs

A collection is served where its route file is. Put the route at `src/pages/products/sdk/[...slug].astro` and the `sdk` collection is served at `/products/sdk/…`: pages, the sidebar, breadcrumbs, Markdown versions, `llms.txt`, the sitemap, search, social cards and, for an API, `openapi.json` and the API catalog. There is no config key; moving a section is moving its folder.

```astro title="src/pages/products/sdk/[...slug].astro"
---
import DocsLayout from "../../../layouts/DocsLayout.astro";
import { getCollectionPage, getCollectionStaticPaths } from "@cloudflare/nimbus-docs/runtime";

export const getStaticPaths = getCollectionStaticPaths("sdk");

const page = await getCollectionPage(Astro);
if (page instanceof Response) return page;
const { entry, Content, headings, markdownUrl, ogImageUrl } = page;
// The rest matches your root src/pages/[...slug].astro: sidebar, previous and next, layout.
---
```

`nimbus-docs add new-collection` writes the whole route for you. Relative imports such as the layout's grow one `../` per folder level.

Nimbus reads the collection from the route's exported `getStaticPaths`: `getCollectionStaticPaths("…")`, `getApiStaticPaths("…")` or `getDocsStaticPaths`, assigned directly (`export const getStaticPaths = …`), or returned from `export async function getStaticPaths()`. A route rendered on request has no `getStaticPaths`, so it names the collection in its page helper instead: `getCollectionPage(Astro, "sdk")`, and likewise `getCollectionPageProps`, `getApiRoute` and `getApiPage`. If a route names it in both, the names must match. Pass the collection name as a string literal, or an exported const holding one. Astro runs `getStaticPaths` apart from the rest of the frontmatter, so anything it uses at the top level must be imported or exported (`export const name = "sdk"`); `export { getStaticPaths }` doesn't compile.

A route Nimbus can't read, such as a wrapper imported from another module, keeps the collection at its default URL. The build and `check` warn about one in a nested folder (`nimbus/collection-unread-route`), and its pages fail the build when they render, naming the route.

The rules:

- `docs` is served at the site root, and a docs version (`docs-v1`) at `/v1`. A docs route away from the root isn't supported yet; for a site that is all docs under one path, set Astro's `base` (`base: "/docs"`).
- Any other collection with a route is served at the route's folder, the root included. Without one, it's served at `/<name>`, as before.
- One route file serves one collection. A route under a dynamic folder (`src/pages/[locale]/sdk/[...slug].astro`) doesn't set a URL; a collection other than `docs` served only from routes like that is an error. Rendered on request, such a route finds its collection by the URL segment before the page, so it serves only collections at a one-segment URL (`/sdk`).
- Several static routes for one collection: the one at its default URL serves it. The others still build their pages (or serve them, for a collection rendered on request), which duplicate the collection's in the sitemap and search, so the build and `check` warn (`nimbus/collection-alias-route`); delete them or redirect them. With none at the default, it's an error.
- A collection a route moved owns everything below its URL. Another collection's page under `/products/sdk` is an error, except under a collection nested deeper (`/products/sdk/cli` is its own). A collection at its default URL (`/sdk`) leaves pages under it as they were.
- An API collection needs a folder: one at the site root is an error for now.

`nimbus-docs check` lists where each collection is served when a route moves one, and `check --json` always includes the list as `collections`.

To link to a collection from a component, use `getCollectionUrl`, which returns the URL without `base`. A name that isn't a page collection fails the build:

```astro
---
import { getCollectionUrl, withBase } from "@cloudflare/nimbus-docs/runtime";
const sdkHref = withBase(await getCollectionUrl("sdk"), import.meta.env.BASE_URL);
---
```

Moving a route moves every URL in that collection, whether it renders at build or on request. Add a redirect from the old URLs (see [Redirects](/navigation/redirects)). Until you do, `nimbus-docs lint` reports links to them as broken and suggests their new URL; after, turn on [`nimbus/redirected-link`](/writing/linting) to find the links still going through the redirect. In `astro dev`, moving a route file restarts the server onto the new URLs and logs the redirect to add. After that restart, Astro can stop showing content edits until you restart the dev server yourself; an `astro.config` edit does the same on a plain Astro site. A collection nested inside a docs folder appears inside that folder in the sidebar, and breadcrumbs and previous and next links follow (see [Nested collections](/navigation/sidebar#nested-collections)). A collection's own `llms.txt` at a nested URL needs the starter's nested section route, `src/pages/[...section]/llms.txt.ts`; the root `llms.txt` and the nearest section above it link to it. With a `[section]` route, the root `llms.txt` lists that collection's pages instead.

### Collection URL errors

The build and `nimbus-docs check` report each of these with the file and the fix; `check` shows the code:

| Code | Cause |
|---|---|
| `nimbus/collection-two-routes` | Several static routes for one collection, none at its default URL. Keep one. |
| `nimbus/collection-same-url` | Two collections at one URL. Move one of their routes. |
| `nimbus/collection-dynamic-folder` | A collection other than `docs` served only from routes under dynamic folders. Give it a static route. |
| `nimbus/collection-docs-route` | `docs` routed away from the site root. Move the route to `src/pages/[...slug].astro`, or set Astro's `base`. |
| `nimbus/collection-version-route` | A docs version routed away from `/<version>`. Move the route there. |
| `nimbus/collection-api-root` | An API collection routed at the site root. Move its route into a folder. |
| `nimbus/collection-route-param` | A route helper in a route whose parameter isn't `slug` (`[...path].astro`). Rename it to `[...slug].astro`. |
| `nimbus/collection-owns-url` | A page under another collection's moved URL. Move the page. |

A page that renders from a route its collection isn't served from fails the build, naming the route's folder and the collection's route file, or the route Nimbus couldn't read. A request-rendered route under a folder no collection is served from returns not found and logs the same advice; one under a dynamic folder (`src/pages/[locale]/kit/[...slug].astro`) isn't reported, since its folder depends on the URL.

## Custom route helpers

Route matching uses logical, unbased paths; links sent to a browser use based paths. Nimbus exports helpers for both sides from `@cloudflare/nimbus-docs/runtime`:

```ts
import {
  entryRouteKey,
  stripBase,
  withBase,
} from "@cloudflare/nimbus-docs/runtime";

const route = entryRouteKey(entry.id);
const requestedRoute = stripBase(Astro.url.pathname, import.meta.env.BASE_URL);
const href = withBase(`/${route}`, import.meta.env.BASE_URL);
```

- `entryRouteKey()` preserves Astro entry IDs while collapsing a final `/index`.
- `stripBase()` removes the configured base before route matching.
- `withBase()` adds the configured base when producing a browser URL.

Nimbus rejects ambiguous or unsafe generated routes during the build. Common causes include both `foo` and `foo/index`, collisions with reserved `llms.txt` routes, encoded path separators, and encoded `.` or `..` segments. The build error names the conflicting entries.

## Page URLs

`getDocsPage()` and `getCollectionPage()` return each page's URLs next to `entry`, `Content`, and `headings`, so page routes don't build them by hand. `getIndexedEntries()` returns the same values on each `IndexedEntry`.

| Field | Example | Description |
| --- | --- | --- |
| `markdownUrl` | `/blog/welcome/index.md` | The page's clean Markdown version. `/index.md` for the site root. |
| `sourceUrl` | `/blog/welcome/index.mdx` | The page's authored source. `undefined` for entries without an authored body. |
| `ogImageUrl` | `/og/blog/welcome.png` | The page's generated OG card. `/og/index.png` for the site root, `/og/blog.png` for the root of a collection mounted at `/blog`. |

The URLs follow the entry ID. Astro's glob loader slugifies file paths, which drops dots: `src/content/docs/1.1.1.1/encryption.mdx` gets the ID `1111/encryption`. Dots are kept where Astro doesn't slugify: a version prefix (`/v1.2/guide/`), an API operation (`payment.succeeded`), or a `slug` frontmatter field, which Astro uses as the ID. `docsCollection()` accepts `slug` without any schema change.

Each URL is site-relative, without Astro's deployment base; the starter's layouts add the base when they emit it. The starter's page route uses the URLs directly:

```astro title="src/pages/[...slug].astro (excerpt)"
---
const page = await getDocsPage(Astro);
if (page instanceof Response) return page;
const { entry, Content, headings, markdownUrl, ogImageUrl } = page;
const socialImage = entry.data.socialImage ?? ogImageUrl;
---
```

`getOgImagePages()` returns the `pages` map for astro-og-canvas's `OGImageRoute`: one entry per indexed page, keyed so the card is written at that page's `ogImageUrl`, with the page's `IndexedEntry` as the value. The starter's `src/pages/og/[...slug].ts` passes it through; see [Customize OG cards](/ai/override-markdown#customize-og-cards).
