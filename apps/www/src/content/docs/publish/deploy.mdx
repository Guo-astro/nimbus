A Nimbus site builds to static files by default, so it runs on any host that serves files. This page covers Cloudflare, which the scaffolder sets up for you, then every other host, then rendering pages on request. It assumes a site created with the [Quickstart](/start-here/quickstart).

Before you publish anywhere, set `site` in `astro.config.ts` to the address readers will use. `nimbus-docs check` warns while it's still the placeholder.

## Cloudflare

A site scaffolded for Cloudflare, the default, has:

- `wrangler.jsonc`, which serves the built `dist/` folder with Workers Static Assets. There's no Astro adapter: a static site doesn't need one.
- Four scripts in `package.json`: `predeploy` runs `astro check` and `astro build`, `deploy` runs `wrangler deploy`, and `preview:cf` builds the site and serves it locally with `wrangler dev`, as Cloudflare will.

Deploy with:

<PackageManagers pkg="deploy" type="run" />

The first run opens a browser to sign in to Cloudflare, then publishes the site at `https://<name>.<your-subdomain>.workers.dev`. To serve it at your own domain, add a custom domain to the Worker in the Cloudflare dashboard, then set `site` to that domain and deploy again.

## Other static hosts

Scaffold with `--deploy other` for a project without `wrangler.jsonc` or the Cloudflare scripts, or delete them from an existing one. Then build:

<PackageManagers pkg="build" type="run" />

and publish the `dist/` folder. Astro's [deploy guides](https://docs.astro.build/en/guides/deploy/) cover the settings for each host. On Vercel and Netlify production builds, Nimbus reads the site's address from the host when `site` is still the placeholder; on any other host, set it yourself.

## Render on request

Some features need a server: rendering pages on request, a [remote MCP server](/ai/remote-mcp), and API references that render on request. Add an adapter for your host:

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add server-output --adapter node" />

`--adapter` takes `cloudflare`, `vercel`, `netlify` or `node`, and `add adapter-node` is the same command. It sets `output: "server"` and installs the adapter. Choose which collections render on request with `rendering` in the Nimbus config; see [Configuration](/reference/configuration#mix-build-and-request-rendering). To start a new site with a server, pass `--adapter` to the scaffolder instead of `--deploy`.

On Cloudflare, the scaffolded scripts stay the same: `deploy` builds and publishes the Worker. On Node, the scaffolder adds a `start` script, `node ./dist/server/entry.mjs`.

Generated API pages render on request on Cloudflare, and on Node with `bundle: false`. [OpenAPI reference pages](/writing/openapi#build-or-request-rendering) covers both, and what each mode publishes for agents.

## Serve under a path

To publish the site under a path, such as `https://example.com/docs/`, set Astro's `base` to `/docs` in `astro.config.ts`. Every page, Markdown version and `llms.txt` moves under it. [Build one locale or one part](/publish/partial-builds#under-a-base) covers serving several Nimbus builds under one hostname.

## Redirects

Redirects in `astro.config.ts` reach every host: on a static host Astro writes a page that sends readers on, and adapters turn them into the host's own rules. For the old Markdown and `llms.txt` URLs, or a site under a `base`, add host rules too. [Redirects](/navigation/redirects#host-level-redirects) shows both.

## Last-updated dates in CI

The "Last updated" line and the sitemap's dates come from git history. Most CI systems clone only the latest commit, so set `fetch-depth: 0` on the checkout step in GitHub Actions, or run `git fetch --unshallow`, before the build. [Metadata and SEO](/publish/metadata-and-seo) has the details.
