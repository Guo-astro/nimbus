Nimbus serves documentation through endpoints that AI tools can read without parsing the HTML site.

## What ships

- **Alternate Markdown/MDX versions for every discoverable page** — `/<slug>/index.md` contains clean Markdown with components converted to text, while `/<slug>/index.mdx` retains imports, JSX, and directives. Nimbus resolves links and reusable snippets during the build. The `.md` version links to its `.mdx` source. API reference pages have only the `.md` version. Hidden versions do not emit either file.
- **A site `llms.txt` index** — names top-level pages and section indexes of the current docs. Each section index links its discoverable pages to their alternate Markdown versions. Older docs versions aren't listed; each has its own index at `/<version>/llms.txt`.
- **`llms-full.txt`** — combines discoverable pages into one Markdown document, excluding non-current prose versions. AI tools and indexing systems can fetch the current site in one request. Nimbus generates it during the build so rebuilds are byte-identical.
- **Per-section indexes at `/<section>/llms.txt`** — each top-level group and collection (e.g. a `blog` or a docs version) gets its own index.
- **Version labels** — on versioned sites, every alternate Markdown version's frontmatter carries a `version:` key (resolved from your `versions` manifest) so agents can pin a version. Unversioned sites emit nothing.
- **JSON-LD in every page head** — structured data so search and agent tools recognize what they're looking at.
- **`/robots.txt` and a sitemap** — wired automatically when `site` is set.

```text title="/llms.txt"
# Nimbus

A way to build documentation sites on top of Astro.

## Pages
- [Get started](https://nimbus-docs.com/get-started/index.md)
- [Installation](https://nimbus-docs.com/installation/index.md)
```

## Agent discovery

Every site serves `/.well-known/ard.json` and `/.well-known/ai-catalog.json` (same content), listing `/llms.txt` and the homepage Markdown at `/index.md`. The homepage also sends `Link` headers for those files and for each visible API reference, through `_headers` on static builds and through middleware when the homepage is request-rendered. Owner `_headers` rules are kept.

`/index.md` is the root content entry when there is one, otherwise the `llms.txt` content. A root entry with `noindex: true` is served but left out of discovery.

If your site already has a file or route at either `.well-known` path, the build fails so you can move your entries first.

Discovery files belong at the origin root. With a `base`, the Cloudflare adapter puts them there for you; on other hosts, deploy the emitted `.well-known` directory at the root alongside the site. Static output with the Cloudflare adapter and a `base` needs `wrangler deploy --assets ./dist/client`.

### Content Signals

The starter's `src/pages/robots.txt.ts` declares `Content-Signal: ai-train=yes, search=yes, ai-input=yes`. Change the values to match your policy; if you set one to `no`, add the policy text from [contentsignals.org](https://contentsignals.org/) above it. Existing sites keep their `robots.txt`; `nimbus-docs upgrade` describes the change. Content Signals and `robots.txt` are requests to crawlers, not access control. Private docs need authentication.

## API catalog and published specs

Sites with API collections serve an [RFC 9727](https://www.rfc-editor.org/rfc/rfc9727) catalog at `/.well-known/api-catalog`, one entry per visible collection and version, linking the reference page, its Markdown, and the published spec. Each spec is published as one self-contained JSON file at its mount path, for example `/pets/openapi.json`; files it references are embedded under an `x-ext` extension. The homepage `Link` header and the discovery manifest point at them.

Set `publishSpec: false` on a collection, or on one version, to keep that spec unpublished; its catalog entry keeps the documentation links. A spec that can't be bundled is skipped with a build warning naming the reference. Hidden versions still publish their file but appear in no catalog, manifest, or header. The catalog file has no extension, so a host that ignores `_headers` needs its own rule for the media type and the `api-catalog` Link on HEAD.

## How pages are indexed

Indexing is multi-collection by default and schema-tolerant — every prepared collection registered in `src/content.config.ts` (except `partials` and reserved names) is walked, reading `title` and `description` when present. There is no per-page opt-in; all discoverable pages are listed. Hidden versions are excluded, and `/llms-full.txt` omits non-current prose versions.

Alternate Markdown/MDX versions and `llms.txt` indexes use public agent-endpoint assets. Request-time authorization cannot make private material safe here. Keep private material outside public content collections. Nimbus omits excluded entries and fails the build when it cannot determine whether content is public.

To keep a page **out** of the `llms.txt` indexes, set `draft: true` (excluded entirely) or `noindex: true`. A page that should never be agent-readable belongs outside the content collection altogether.

### Custom content loaders

Nimbus's collection factories prepare Markdown automatically. If a custom loader retains Markdown bodies for alternate Markdown versions or `llms-full.txt`, wrap it with `withNimbusMarkdown()` from `@cloudflare/nimbus-docs/content`. See [Other collections](/writing/pages-and-routing#other-collections) for a complete example.

## Route setup

New projects include these routes. To add or update them in an existing project, follow [Markdown and llms.txt endpoints](/ai/publish-markdown).

## AGENT.md

The scaffolder writes an `AGENT.md` at the project root — the same context a coding agent reads when working in your repo. It's a real file you maintain; keep it in sync with your project's conventions.

## Why it matters

The cost of being a dead end on the agent web is real and growing. Because these files and metadata are defaults, a Nimbus site is legible to agents the day it ships — see [Metadata and SEO](/ai/metadata-and-seo) for the human-search side.
