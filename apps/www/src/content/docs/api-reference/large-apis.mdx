By default, every API page includes the whole navigation tree. For a large API, that tree can be most of each page's size. Set `sidebar` on the `api` entry to include less:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    spec: "./src/api/openapi.yaml",
    sidebar: "on-demand",
  },
],
```

| Value | What each page includes | A collapsed group |
| --- | --- | --- |
| `"full"` (default) | The whole tree. | Opens in place. |
| `"on-demand"` | Top-level items, plus the current page's branch. | Opens in place, loading its rows the first time. |

With `"on-demand"`, the current page's ancestors are open and show all their children, so its neighbors are one click away. Schema and webhook pages show top-level items only. The setting applies to every version of a family.

When a reader opens a collapsed group, the sidebar fetches the page its label links to and copies the group's rows from that page's sidebar. A group without a page, such as an `x-tagGroups` category, takes its rows from the API overview instead. Fetching starts when the pointer moves over a group or it receives focus, so rows usually appear as soon as it opens. If they cannot load, opening the group goes to its page instead.

Without JavaScript, a collapsed group's label still links to its page. Categories from `x-tagGroups` have no page to link to, so they open only on pages inside them; the API overview's body links every section.

Every page still carries every top-level item, so an API with hundreds of flat tags stays heavy. Group its tags under a tag's `parent` or with `x-tagGroups`, which Nimbus reads in any OpenAPI version. A tag's `x-displayName` sets the label readers see, while its `name` keeps deciding its coordinate and route:

```yaml title="openapi.yaml"
tags:
  - name: workers
    x-displayName: Workers
  - name: workers.scripts
    x-displayName: Scripts
    parent: workers
```

In every mode, the sidebar keeps the groups a reader opened and its scroll position from page to page for the rest of the session, in the desktop rail and the mobile drawer. Restored groups appear already open. Rows loaded on one page show on the next before it paints; a new deployment starts over, so rows saved before it are never shown after it.

The API rail renders the same markup as the docs sidebar: groups are native `<details>`/`<summary>` rows styled by position (`[data-nb-api-nav] li > a`, `details > summary`, `details > ul`) in `src/styles/globals.css`, a group's page lists as its first "Overview" child, and each page renders one tree that the mobile drawer borrows while open. See [Restyle sidebar rows](/navigation/sidebar#restyle-sidebar-rows).

Set `sidebar` on the `api` entry in the Nimbus config. A site that passes its entry to `apiCollection({ … })` still takes the mode from the config, and the build warns if the two disagree.

Every group page lists its operations and its subsections, and the [API home](#the-api-home) lists every operation, so all pages stay reachable in every mode.

`"on-demand"` needs the `api-layout` and `api-sidebar` components from your installed release; the build names outdated files.

## The API home

The API home lists every operation and webhook of the version, the way a section page lists its own: each `x-tagGroups` group a heading, in the spec's order, each section its linked title and description, then its operations, name first with the method and path beneath. Sections in no group come after the groups, then operations without a tag, then webhooks. A filter at the top searches every endpoint: Enter opens the first match and Escape clears it.

A large spec loads in parts. The page holds the first `API_HOME_CHUNK_SIZE` endpoints, 150 unless you change it in `src/components/ui/api-layout/home.ts`, keeping sections whole where they fit and splitting a larger one into continued parts. Each later part is a page of its own, which the home fetches as the reader nears the end; without JavaScript, the list ends in a link to the next part. The filter fetches a compact list of every endpoint the first time it's focused, so it finds endpoints that haven't loaded, and shows up to 200 matches. Browser find-in-page searches only the parts that have loaded.

The parts and the filter's list come from two routes the [recipe](/api-reference/openapi/setup#install-with-the-recipe) writes under `src/pages/nimbus-api/home/<collection>/`, served at `/nimbus-api/home/<collection>/<version>/<n>/` and `…/<version>/index.json`, with `default` as the version of an unversioned API. They render like the collection's pages, built or on request, and the part pages are `noindex`.

## Render on request

API HTML is prerendered by default. To render only the API collection on request, add this policy to the Nimbus config:

```ts title="astro.config.ts"
rendering: {
  default: "build",
  collections: {
    api: "request",
  },
},
```

Then run the Cloudflare adapter installer. It keeps an existing rendering policy. Without one, it sets `rendering: { default: "request" }`, which renders every collection on request.

<PackageManagers pkg="@cloudflare/nimbus-docs" type="exec" args="add adapter-cloudflare" />

Astro then logs "getStaticPaths() ignored in dynamic page" for the request-rendered API route. The warning is expected; see [Choose build or request rendering](/reference/rendering).

The recipe's API catch-all uses Nimbus runtime helpers to resolve either mode. Alternate Markdown versions and `llms.txt` indexes follow the rendering policy too, serving content prepared at build time. Coordinate data, search records, and sitemaps stay build output, and requests read prepared content entries rather than parsing the OpenAPI document.

## Many versions

A request-rendered API bundles its page data into the server. That suits most APIs. For a very large spec, or one that keeps many versions, set `bundle: false` on its entry so the server bundle stays small however many versions you add:

```ts title="astro.config.ts"
api: [
  {
    collection: "api",
    versions: [/* … */],
    bundle: false,
  },
],
rendering: {
  collections: { api: "request" },
},
```

Nimbus then writes each page's data as static assets beside the site, shares unchanged pages between versions, and reads one version's index plus the requested page on each request. Each build also ships the previous successful build's page files, so a server still running that release during a rollout (for example a Node server in a blue-green swap) keeps working; on Cloudflare each Worker version already keeps its own files. The build suggests `bundle: false` when an API's bundled page data passes 16 MiB.

Pages are read through an Astro live collection, which Astro only accepts from your own `src/live.config.ts`. Add it once; the build shows this snippet if it's missing:

```ts title="src/live.config.ts"
import { defineLiveCollection } from "astro:content";
import { apiPagesLoader } from "@cloudflare/nimbus-docs/live";

export const collections = {
  apiPages: defineLiveCollection({ loader: apiPagesLoader() }),
};
```

When Astro's route cache is enabled, each page is cached with the tags `nimbus-api:<collection>` and `nimbus-api:<collection>@<version>`.

`bundle: false` needs the collection rendered on request and the Cloudflare or Node adapter; the build explains what to change otherwise. It also changes discovery for that API: search, `llms.txt`, `llms-full.txt`, the sitemap and Markdown versions cover the default version only. Every version still publishes its spec unless `publishSpec: false` or publication fails, and visible versions are listed in the API catalog. Older versions stay readable as HTML, with `noindex`, and their Markdown returns 404.

With `bundle: false`, Nimbus reuses the versions you didn't change. In CI, restore `.nimbus/cache/page-assets/` before the build and save it after a successful deploy, not after preview builds, so "previous" means the live release; restore the whole directory. Key the cache by project, with a fallback key so adding a version keeps the earlier entries. Nimbus checks the cache's contents itself and rebuilds anything missing or damaged, so keep your specs in the repository, not only in the cache. Upgrading Nimbus can rebuild every version once.

API pages show the sidebar filter; press `/` to focus it. With `sidebar: "full"` it filters the sidebar in place, matching titles and HTTP methods. With `sidebar: "on-demand"`, the sidebar holds only part of the API, so the filter loads a small list of the version's pages the first time you focus it or type, then matches titles, methods and paths locally. Results link to the page in the version you're reading. Each build also ships the previous release's lists, so a tab left open across a deploy keeps filtering; in CI that needs `.nimbus/cache/page-assets/` restored as described above, for bundled APIs too.
